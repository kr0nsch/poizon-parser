# Парсер thepoizon.ru — обувь бренда в вашем размере

Выбираете бренд, вводите длину стопы в сантиметрах — получаете список обуви,
которая **есть в наличии**, с ценой за именно ваш размер и фотографией.
Перевод идёт по официальным таблицам Nike, Adidas, New Balance и ASICS.

Бэкенд работает на стандартной библиотеке Python 3.9+. Современный
веб-интерфейс находится в `frontend/` и собран на Vite 8, React 19,
TypeScript, Tailwind CSS 4 и TanStack Query. Для запуска готовой сборки Node.js
не нужен: Python-сервер раздаёт статические файлы самостоятельно.

Требования:

- **Python 3.9+** — CLI, API и локальный production-сервер;
- **Node.js 20.19+** и **pnpm** — только разработка, тестирование и сборка
  фронтенда.

## Быстрый старт: веб-интерфейс

Соберите современный интерфейс один раз и запустите Python-сервер:

```bash
cd frontend
pnpm install
pnpm build
cd ..
python main.py web
```

Откроется `http://127.0.0.1:8765/`. Сервер автоматически использует
`frontend/dist`, если сборка существует. Если её нет, он запускает сохранённый
интерфейс из `web/index.html`, поэтому CLI и веб-сервер остаются работоспособны
без Node.js и без предварительной сборки.

Интерфейс содержит два основных раздела:

- **Поиск** — бренд (автодополнение по 4000+ брендам сайта), длина стопы в см,
  сетка (мужская/женская), глубина (40 / 120 / весь каталог), цена и
  темп запросов. Отдельный переключатель оставляет в подсказках только бренды,
  чьи размерные ряды сверены с официальным сайтом производителя. Пока вводите —
  **живой калькулятор** сразу показывает ваш размер
  в выбранном бренде (EU / US / UK / ярлык) и у трёх остальных для сравнения, не
  дожидаясь поиска. Форма запоминается между заходами. Результаты появляются на
  лету, с фото, ценой, сроком доставки, прогрессом и ETA. **Живой монитор** под
  прогрессом показывает, что парсер делает прямо сейчас (грузит карточку, ждёт
  очередь, пережидает лимит), индикатор-пульс и «активность N c назад» — видно,
  что идёт работа, а не зависание, и почему встало. Долгий поиск можно остановить
  «Стоп» или поставить на паузу, пройти проверку на сайте и продолжить.
  Найденное фильтруется, сортируется и выгружается в CSV/JSON.
- **Итоги** — отобранные кнопкой «☆ В итоги» позиции: фото, каким запросом
  найдено, когда сохранено. Выборка **личная у каждого пользователя** (см.
  многопользовательский режим ниже), переживает перезапуск, выгружается в CSV
  (для Excel) и JSON.

Кнопка **«📄 HTML-отчёт»** собирает результаты в один самодостаточный HTML-файл в
папке `result/` — его можно переслать кому угодно, получатель откроет в браузере и
увидит все модели с фото, ценами, размерами и ссылками на POIZON (плюс сортировка
и фильтр прямо в файле). Галочка «с фото офлайн» вшивает картинки в файл, чтобы он
открывался без интернета.

Мелочи для стабильности: ввод длины стопы проверяется (15–40 см — иначе понятная
ошибка, а не пустой результат), завершённые задачи не копятся в памяти (последние
20), есть эндпоинт `/api/health`.

## Две вещи, которые ломают наивный подбор

**1. Размер «42» на POIZON — это не 42 производителя.** Сайт подписывает каждый
товар двумя шкалами, и его «RU» равен EU минус единица. Если вы носите Nike EU 42,
на POIZON это лежит под ярлыком **«RU 41 / EU 42»** — выбрав там «RU 42», вы
получите обувь на размер больше. Поэтому размер задаётся длиной стопы, а в выдаче
всегда показан полный ярлык POIZON, чтобы можно было сверить глазами.

**2. Цена привязана к размеру, а не к модели.** Каждый размер выставляют разные
продавцы, поэтому у одной пары 41-й может стоить 7 050 ₽, а 44,5 — 19 490 ₽.
«Цена от» на карточке — минимум по всем размерам, и к вашему размеру она обычно
отношения не имеет. Парсер берёт цену конкретного размера.

## Размер задаётся длиной стопы

В интерфейсе одно поле — **длина стопы в сантиметрах**. Это самый однозначный
вход: «42» у разных брендов означает разную обувь, а 26,2 см — это 26,2 см.

```
замер стопы, см
      ↓  официальная таблица бренда + сетка (муж./жен.)
   EU-размер этого бренда
      ↓  ярлыки SKU на POIZON
   конкретная пара в наличии + цена
```

Как мерить: встаньте на лист бумаги пяткой к стене, отметьте самый дальний палец,
измерьте от края листа до отметки. Вечером и обе ноги — берите большее значение.
Запас на посадку уже заложен в таблицах производителей, прибавлять ничего не надо.

В CLI сантиметры тоже по умолчанию, а другие шкалы остались для тех, кто точно
знает свой размер:

```bash
python main.py shoes -b nike -s 26,5              # по стопе
python main.py shoes -b nike -s 42 --scale EU     # если знаете EU
python main.py shoes -b adidas -s 9 --scale "US M"
```

### Две разные величины в сантиметрах

Это главный подвох, из-за которого наивный перевод ошибается на размер:

| Nike, US M 9 | |
|---|---|
| ярлык размера («CM / JP») | **27,0 см** |
| реальный замер стопы («Foot Length») | **26,2 см** |

Парсер ищет по **замеру**, а в карточке показывает **ярлык** (чип «ярлык 27 см») —
по нему удобно сверяться с POIZON, который печатает ту же величину.

Nike и Adidas публикуют обе колонки, поэтому для них перевод идёт напрямую.
New Balance и ASICS публикуют только ярлык — для них замер стопы сначала
переводится в US по шкале Брэннока (её даёт таблица Nike, где есть обе колонки),
а US в EU уже по собственной таблице бренда. Так сохраняются реальные различия
брендов — они как раз в соответствии US → EU. Об этом честно пишется в строке
статистики под прогрессом.

Проверка сходимости: замер 26,2 см даёт EU 42,5 у Nike, NB и ASICS и EU 42⅔ у
Adidas — то есть одну и ту же пару.

## Официальные таблицы брендов

Для **Nike, Adidas, New Balance и ASICS** размер переводится по их собственным
официальным сеткам, а не по усреднённой.

Это важно, потому что бренды **не совпадают** между собой:

| US муж. | Nike | Adidas | New Balance | ASICS |
|---------|------|--------|-------------|-------|
| 8  | EU 41   | EU 41⅓  | EU 41,5 | EU 41,5 |
| 9  | EU 42,5 | EU 42⅔  | EU 42,5 | EU 42,5 |
| 11 | EU 45   | EU 45⅓  | EU 45   | EU 45   |
| 13 | EU 47,5 | **EU 48** | EU 47,5 | **EU 48** |

Мужская и женская сетки хранятся раздельно — у New Balance они расходятся между
собой даже для одного US-размера. Выбирается флагом `--gender` (в вебе — «Сетка»).

Посмотреть таблицу:

```bash
python main.py brandchart              # какие таблицы есть
python main.py brandchart adidas
python main.py brandchart nike --gender women
```

Источники и как пересобрать:

| Бренд | Источник |
|-------|----------|
| Nike | `nike.com/size-fit/mens-footwear` (блок `sizeCharts` в HTML) |
| Adidas | `adidas.com/us/help/size_charts`, вкладка Shoes |
| New Balance | `newbalance.com/size-guide.html` |
| ASICS | `asics.com` shoe size guide |

```bash
python tools/build_size_charts.py [путь_к_xlsx]
```

Данные лежат в `poizon_parser/data/size_charts.json` — обычный JSON, при желании
правится руками. В строке хранятся `us`, `uk`, `eu`, `cm` (колонка CM/JP
производителя) и `foot` (чистый замер стопы, где бренд его публикует). У
New Balance официальный `Length (cm)` сохраняется как `foot`; мужская/унисекс
и женская сетки обрабатываются раздельно. Для брендов **без** официальной
таблицы (Puma, Vans, Converse…) работает общая атлетическая сетка с пометкой
«≈».

## Про размерные шкалы

В SKU сайт публикует только две шкалы — **RU и EU**, причём его RU = EU − 1.
Шкал US / UK / CM в карточках товара нет вообще.

Порядок источников перевода — от достоверного к запасному:

1. **Официальная таблица бренда** (Nike / Adidas / New Balance / ASICS) — см. выше.
2. Таблица самого товара из карточки POIZON (`sizeAssistantModule`, 3 опорные строки).
3. Встроенная эталонная атлетическая лестница на весь диапазон.
4. Типовое смещение.

Всё, что переведено не из точной строки таблицы, помечается «≈», и рядом стоит
ярлык POIZON — сверьте по ссылке перед заказом.

**«US» и «US мужской» — это одно и то же.** В кроссовочном контексте «US» без
уточнения означает **мужскую** шкалу, и в коде `US` → `US M`. Женская шкала
(`US W`) для той же пары примерно на 1,5 размера больше: US W 5 и US M 3,5 — это
одна обувь (EU 35,5).

Поэтому **размер 13** переведётся так (мужская сетка, по бренду):

| Ввод | Как понято | Nike | Adidas | NB | ASICS |
|------|-----------|------|--------|-----|-------|
| `13` + `US M` (или `US`) | мужской 13 | EU 47,5 | EU 48 | EU 47,5 | EU 48 |
| `13` + `US W` | женский 13 | EU 45,5 | EU 46⅔ | EU 45,5 | вне сетки |
| `13` + `UK` | UK 13 | EU 48,5 | EU 48⅔ | EU 48,5 | вне сетки |
| `13` + `EU` | EU 13 — не бывает | ничего не найдётся | | | |

«Вне сетки» — размера нет в официальной таблице ASICS (женская заканчивается на
US 12, мужская UK — на 14): тогда парсер откатывается на общую лестницу и
помечает результат «≈».

Колонка «Посадка» — рекомендация сайта для конкретной модели (`-0,5` значит
«маломерит, берите на полразмера меньше»).

Если вы точно знаете свой размер в EU, используйте его: перевод не потребуется.

### Команда `find` и её шкалы

У `find` (поиск по названию) логика другая — она сопоставляет размер напрямую с
теми шкалами, что подписаны в SKU, без перевода:

Логика подбора:

1. Если указан `--scale`, ищем только в этой шкале.
2. Иначе берём шкалу, которую сайт показывает для этой модели по умолчанию
   (обычно RU).
3. Если в ней такого размера нет — переходим к следующей шкале, а в выводе
   явно пишем, в какой шкале нашли (`42,5 EU`). Отключается `--strict-scale`.

Шкалы никогда не смешиваются внутри одного сравнения: выбирать «где дешевле»
между RU 42 и EU 42 нельзя — это обувь разной длины. Если в итоговой таблице
оказались разные шкалы, парсер предупредит об этом отдельной строкой.

Дробные размеры вида `42⅓`, `41⅔`, `34½` (Adidas и др.) разбираются корректно и
не приравниваются к целым.

## Использование из кода

```python
from poizon_parser import PoizonClient, SizeFinder
from poizon_parser.catalog import Catalog

client = PoizonClient(delay=1.0, cache_dir=".cache")
finder = SizeFinder(client)

# Основной сценарий: обувь бренда в размере EU 42
for match in finder.find_by_brand("nike", size="42", scale="EU", limit=10):
    print(match.product.title, match.offer.price, match.offer.size_label)

# Список брендов
for brand in Catalog(client).brands()[:5]:
    print(brand.brand_id, brand.name, brand.slug)

# Все размеры конкретной модели
product = finder.load_product(8900001978861819)
for offer in product.in_stock_offers():
    print(offer.sizes, offer.price, offer.delivery)
```

`find()` возвращает список `Match`; у каждого есть `.product`, `.offer`,
`.matched_scale` и метод `.to_dict()` для сериализации.

## Как парсер не нарывается на блокировки

Главный приём — **делать меньше запросов и держать ровный темп**, а не пытаться
обмануть защиту. Что для этого сделано:

| Приём | Что даёт |
|-------|----------|
| **Ограничитель частоты** (token bucket, общий на все потоки) | сколько бы воркеров ни работало, темп запросов не превысит заданный |
| **Параллельность 3 воркера** | перекрывает сетевые задержки, **не повышая** частоту запросов |
| **Предфильтр по цене** | если минимум по всем размерам уже дороже лимита, карточка не грузится вовсе |
| **Дисковый кэш** | повторный прогон с другим размером не тянет каталог заново |
| **Авто-откат по `Retry-After`** | 429 пережидается сам, без участия человека |
| **Адаптивное замедление** | после каждой проверки пауза растёт (до +4 c) и спадает после успехов |

Эффект видно в строке статистики под прогрессом. Реальный прогон
(New Balance, EU 42, лимит 7000 ₽, 40 моделей):

```
запросов к сайту: 0 · из кэша: 26 · отсеяно по цене: 16
```

Ноль обращений к сайту: 16 карточек отсеяны по цене из листинга, остальные взяты
из кэша. Чистый прогон без кэша — 40 карточек за 26 с, **0 срабатываний лимита**.

Темп выбирается в интерфейсе («Бережно» / «Обычный» / «Быстрее») или флагами
`--delay` и `--workers` в CLI.

Чего парсер **не** делает: не решает капчи, не крутит прокси и не подменяет
отпечаток браузера. Это обход защиты, а не парсинг; вместо этого он ведёт себя
как вежливый клиент и честно останавливается, когда сайт просит.

## Что происходит прямо сейчас (мониторинг)

Чтобы поиск не выглядел «намертво зависшим», под прогрессом идёт **живой монитор**:

- строка «сейчас» — что делает парсер в эту секунду: `загружаю карточку (NB-530)`,
  `жду очередь запроса — пауза 15 c`, `⏳ сайт ограничил частоту, жду 30 c`,
  `↻ сеть не ответила, повтор через 4 c`, `🛡 требуется проверка`;
- **индикатор-пульс** и «активность N c назад» (считает сервер) — зелёный, пока
  идёт работа; жёлтый при ожидании; красный, если ответа нет дольше 20 c;
- при **необъяснённом застое** (>20 c без ответа и это не известный лимит) —
  прямое предупреждение с диагнозом и что делать;
- в конце — **причина остановки**: «готово: проверено N из M», «остановлено
  пользователем», «сайт требует проверку», «ошибка …».

Так видно и этап (сбор каталога / проверка карточек), и почему прогресс мог
замедлиться или встать.

## Капча и ограничение частоты

При частых запросах POIZON отвечает **HTTP 429 / 403** или показывает проверку
(капчу). Сначала парсер пробует **пережить это сам**: читает заголовок
`Retry-After` (но ждёт не дольше 90 с, даже если сайт просит больше), ставит
общую паузу для всех потоков и повторяет (до 3 раз). В мониторе и строке
прогресса при этом тикает «пауза N c» — вмешиваться не нужно, поиск не завис.

**«Стоп» работает всегда, мгновенно** — даже посреди долгой паузы после 429:
ограничитель частоты просыпается каждые полсекунды, так что поиск прекращается за
~1 секунду.

**Ручной режим капчи.** Кнопкой **«⏸ Пауза / пройти проверку»** можно в любой
момент остановиться самому — даже если авто-определение проверку не поймало.
Парсер встаёт (прерывая и текущее ожидание лимита за ~1 c), показывает ссылку на
сайт: откройте, пройдите капчу вручную в браузере, вернитесь и нажмите
**«Продолжить»** — поиск идёт дальше с того же места.

Если проверку не удалось пройти автоматически — парсер не падает, а **ставит
поиск на паузу** тем же баннером:

- **В вебе** — баннер с кнопкой «Открыть проверку в новой вкладке» (открывается
  отдельной вкладкой, чтобы не терять поиск) и «Продолжить»; ничего не теряется.
  Можно и «Отменить поиск».
- **В терминале** (`shoes`) парсер печатает ссылку и ждёт: пройдите проверку и
  нажмите Enter (или `q` — прервать).
- Между запросами держится пауза, которая **автоматически растёт** после каждой
  проверки (до +4 с) и спадает после серии успехов — чтобы не провоцировать
  блокировку. C3VK-заглушку сайта парсер проходит сам, без участия человека.

Важный нюанс: парсер и ваш браузер — разные сессии cookie. «Продолжить» помогает,
когда блокировка по IP (после капчи в браузере сайт снимает ограничение с адреса) —
это типичный случай 429. Если проверка требует именно cookie, увеличьте паузу
(`--delay`) и глубину поменьше.

Про большие каталоги: «Весь каталог» у крупного бренда — это **сотни карточек**
(у Nike их больше тысячи), и цена/наличие есть только внутри каждой, поэтому
прогон идёт минуты, а под лимитом дольше. Интерфейс об этом предупреждает,
показывает прогресс, ETA и паузы, и поиск можно остановить в любой момент —
найденное останется. Ускоряет дело фильтр по цене (карточки дороже лимита не
грузятся) и кэш (повторный прогон почти мгновенный). Обход идёт **порциями**,
а не «всё разом»: лимит и отмена срабатывают сразу, а не после очереди из тысяч
заданий.

Как это устроено: `PoizonClient(on_challenge=callback)`. Колбэк вызывается при
непроходимой автоматически проверке, **блокируется** до сигнала пользователя и
возвращает `True` (повторить) или `False` (прекратить). Веб-задача реализует его
через `threading.Condition` со счётчиком поколений (безопасно для нескольких
воркеров), терминал — через `input()`. Детектор проверки
(`_detect_challenge`) опирается на то, что легитимные страницы всегда содержат
`__NEXT_DATA__`.

## Как это устроено

Сайт отдаёт данные тремя путями, и парсер использует все:

1. **Страницы каталога** `/brand/list`, `/brand/<slug>?page=N`,
   `/category/<slug>` — рендерятся на сервере, список товаров лежит прямо в
   `__NEXT_DATA__`. Бренд задаётся адресом страницы.
2. **Страница товара** `/product/<slug>-<spuId>` — там же в `__NEXT_DATA__`
   лежат цены по каждому размеру и официальная таблица размеров. В JSON-ответе
   карточки (`get-index-spu-detail`) у SKU полей с ценой нет вовсе.
3. **JSON API** `/api/v1/h5/home-page/intl/landing/search/page` — поиск по
   названию. Каждый запрос подписывается параметром `sign` =
   `md5(отсортированные пары ключ-значение + соль)`; алгоритм повторён в
   `client.calc_sign()`.

Категория отбирается по `level1CategoryId` (29 — «Обувь», 1003733 — детская).
Фильтры сайта по бренду и размеру через URL не применяются: SSR игнорирует
query-параметры, а клиентский эндпоинт фильтрации отдаёт рекомендательную
выдачу без учёта переданных фасетов — проверено, результаты не меняются.
Поэтому размер отбирается на нашей стороне, по карточкам.

Чтобы перебор бренда не бил по сайту дважды, HTML кэшируется на диск
(`--cache-ttl`, по умолчанию 15 минут; `--no-cache` отключает).

### Веб-интерфейс

`python main.py web` поднимает локальный сервер (`poizon_parser/webapp.py`,
чистый `http.server` из stdlib). В production-режиме он автоматически раздаёт
сборку из `frontend/dist`; если каталога сборки нет, используется legacy-страница
`web/index.html`.

Исходники современного интерфейса находятся в `frontend/`:

- Vite 8 отвечает за dev-сервер и production-сборку;
- React 19 и TypeScript — за интерфейс и типизацию;
- Tailwind CSS 4 — за стили и дизайн-токены;
- TanStack Query — за серверное состояние, мутации и опрос фоновой задачи.

Для разработки запустите API и Vite в двух терминалах:

```bash
# терминал 1 — Python API
python main.py web

# терминал 2 — frontend
cd frontend
pnpm install
pnpm dev
```

Dev-интерфейс откроется на `http://127.0.0.1:5173/`; запросы `/api` и
`/result` проксируются на Python-сервер. Production-сборка создаётся командой:

```bash
cd frontend
pnpm build
```

Результат записывается в `frontend/dist` и подхватывается Python-сервером без
копирования файлов и отдельного Node.js-процесса.

Поиск — долгая операция, поэтому оформлен фоновой задачей:
`POST /api/search` возвращает id, а фронтенд опрашивает
`GET /api/search/<id>` и дорисовывает найденные карточки на лету. Прочее API:
`GET /api/brands` (кэш 6 часов), `GET/POST/DELETE /api/picks` — личные
избранные (см. ниже).

Глубина «Весь каталог» проходит все страницы листинга бренда
(60 товаров на страницу; проверено на New Balance — 980 моделей обуви).

### Многопользовательский режим

Сервисом могут одновременно пользоваться несколько человек — например, если
запустить сервер на всю сеть:

```bash
python main.py web --host 0.0.0.0
```

и открыть с других ПК по адресу `http://<IP-хоста>:8765/`. У **каждого свои
избранные**: при первом заходе сервер выдаёт анонимный идентификатор в cookie
(`poizon_uid`), и «Итоги» хранятся отдельно — `data/picks/<uid>.json`. Поиски
изолированы сами по себе (каждый опрашивает свой `jobId`), а кэш страниц сайта
общий — если один уже загрузил каталог бренда, остальным он достанется из кэша.

Идентификатор анонимный, без логина и пароля; в cookie только случайный id, сами
избранные лежат на сервере. Кто в одной сети — тот и пользователь, аутентификации
нет, так что открывать сервер в публичную сеть не стоит.

Размеры собираются так: `goodsDetail.saleProperties` даёт словарь
`propertyValueId → значение` для каждой шкалы, а `priceInfo.skuInfoList` —
список SKU, где у каждого есть ссылка на `propertyValueId` размера и `minPrice`.
Соединение этих двух структур и даёт «размер → цена».

Перед выдачей HTML сайт иногда отвечает заглушкой, которая ставит одноразовую
cookie `C3VK`; клиент читает её и повторяет запрос автоматически.

Между запросами выдерживается пауза (`--delay`, по умолчанию 0.7 с), при
сетевых ошибках и 5xx — до трёх повторов с нарастающей задержкой.

## HTML-отчёты (`result/`)

`report.py` собирает результаты в самодостаточный HTML-документ: стили встроены,
разметка статична (карточки видны даже без JS), а лёгкий встроенный скрипт даёт
сортировку и фильтр. Названия товаров экранируются. Отчёты складываются в
`result/<бренд>-<размер>-<дата>/index.html` — каждый прогон в свою папку.

Фото по умолчанию грузятся с CDN сайта (файл лёгкий, картинки видны при
интернете); `--embed-images` / галочка «с фото офлайн» скачивает их и вшивает в
файл как `data:` URI — тогда отчёт полностью автономен. Сервер отдаёт готовые
отчёты по `/result/...` (с защитой от выхода за папку) для предпросмотра.

Папка `result/` создаётся при первом отчёте; её можно смело удалять или не
класть в систему контроля версий.

## Ограничения

- **Перевод из US / UK / CM приблизителен** за пределами трёх опорных строк
  официальной таблицы модели — такие строки помечаются «≈». Если знаете свой
  размер в EU, укажите его.
- Цена и наличие есть только в карточке товара, поэтому каждая модель
  загружается отдельно (~0,6 с на карточку). Режим «Весь каталог» у крупного
  бренда — это сотни карточек и несколько минут; прогресс виден, поиск можно
  остановить, а повторный прогон ускоряет дисковый кэш.
- Разбор опирается на структуру `__NEXT_DATA__`; при редизайне сайта её
  придётся обновить (см. `extract.py`).
- Цены и наличие меняются постоянно — результат актуален на момент запуска.
- Указанная цена не включает возможную таможенную пошлину: сайт добавляет её
  при оплате для товаров дороже 200 €.
- Парсер только читает публичные страницы: авторизации, корзины и оформления
  заказа здесь нет.
